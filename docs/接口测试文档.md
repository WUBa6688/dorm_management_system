### 1.3 如何用于开发

1. 后端先核对第 3、4、10、12 章，提交实际请求及响应样例。未定义路径、字段或传输方式的项目标记“契约待定”。
2. 前端按冻结版本封装请求，使用一致的业务模型；数据库内部状态由后端转换，不直接当作页面状态。
3. 使用第 2 章独立测试数据，先执行第 5 章 P0，再执行第 6 章业务用例及第 7 章跨模块用例。
4. 第 4 章所有路径和字段均为**建议契约**，其中沿用 S2 的路径也不代表已实现。第 10 章对照现存 SQL，补充后端映射和对账入口。
5. 目前所有用例初始结果均为“未执行”。接口不存在记“未实现”；环境或契约不齐记“阻塞”，不能记为通过。

## 3 新契约公共约定

本章为前后端可采用的建议值；S1 明确要求的 401、403、权限、一致性及业务边界不因字段命名变化而改变。正式采用时在第 12 章登记冻结版本。

### 3.1 请求与认证

- `GET` 参数放在 URL Query 中；`POST`、`PUT` 默认使用 `Content-Type: application/json; charset=UTF-8`，不使用 GET 请求体。
- 暂按 Session 登录：登录成功后接收服务端 Cookie，后续由 Cookie Jar 自动发送；Cookie 名称、有效期和 CSRF 策略由后端填写，不能假定固定名称。修改类请求如启用了 CSRF，须同时携带实际配置的 CSRF 凭据。
- 同源代理下浏览器自动带 Cookie；直接跨源联调时前端需配置凭据传递，后端需允许明确的来源和凭据。以浏览器实际请求验证，Postman 成功不能证明跨域配置正确。
- 用户身份和授权范围从服务端登录状态取得。学生不得通过修改 `studentId`、学号或请求体中的角色冒用他人。
- 停用账号、重置密码使该账号所有既有会话失效；退出只结束当前会话；宿管授权变化从下一次请求起生效。

### 3.2 响应与分页

正常响应建议统一为 HTTP 200，`code=0`。创建接口应返回新记录 ID，便于后续请求关联；无业务数据时 `data=null`。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": "1001"
  }
}
```

分页请求使用 `page`、`pageSize`，页码从 1 开始。建议默认每页 15 条，上限 100 条；这是本稿建议限制，不是来源已确定的实现。过滤后再计算总数；空列表和超出末页返回空数组，不返回其他范围的数据。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "page": 1,
    "pageSize": 15,
    "total": 0,
    "records": []
  }
}
```

### 3.3 错误断言

| HTTP | 建议业务码 | 适用情形 | 必测断言 |
|---|---|---|---|
| 400 | 40001 | 必填缺失、类型错误、非法枚举、日期或范围错误 | 说明可定位到字段；无部分写入 |
| 401 | 40101 | 未登录、凭据失效、账号被停用、重置后旧会话 | 无受保护业务数据；前端清理登录态并进入登录流程 |
| 403 | 40301 | 已登录但角色、本人或楼栋范围不允许 | 返回 403，不泄露对象内容，不改变数据 |
| 404 | 40401 | 已通过权限校验、范围内对象不存在 | 不生成空记录；前端提示对象不存在或刷新 |
| 409 | 40901 | 唯一性冲突、床位冲突、过期状态、重复处理 | 可重新查询当前状态；原有有效数据不被破坏 |
| 500 | 50001 | 非预期服务端异常 | 通用错误信息；不返回堆栈、SQL、密码或凭据；关键事务回滚 |

建议错误体为 `{"code":40901,"message":"目标床位已占用","data":null}`。业务码数值、400 与 409 的细分须在冻结时确认；401、403 遵循 S1。测试不依赖完整中文错误字符串，但须能分辨错误原因。越权对象按 S1 返回 403；不存在与越权并存的探测场景需统一处理顺序，不能先返回对象详情。

### 3.4 字段和时间

| 项目 | 新契约建议 | 测试要点 |
|---|---|---|
| 字段名称 | camelCase | 不混用 `student_no`、`studentNo`、`studentId` |
| ID | JSON 中使用十进制字符串 | 避免 BIGINT 在浏览器中丢失精度；统一序列化，不能混用数字和字符串 |
| 业务编号 | 学号、房号、床号为字符串 | 前导零不得丢失；数据库 ID 与业务编号不得混用 |
| 时间 | `yyyy-MM-dd HH:mm:ss`，明确为 Asia/Shanghai 本地时间 | 不把该格式误认为自带时区的 ISO 8601；跨端解析不得发生 8 小时偏移 |
| 日期 | `yyyy-MM-dd` | 日期区间含起止日，查询实现为开始日 00:00 至结束日次日 00:00 之前 |
| 分数 | 0 至 100 的 JSON 整数 | 拒绝负数、101、小数和非数字 |
| 百分比 | 以百分数数值返回，保留 1 位小数；无分母返回 `null` | 例如 60.0 表示 60.0%；前端格式化为 `60.0%`，null 显示“—” |
| 状态 | 固定英文枚举，见第 4 章 | 拒绝任意字符串；不以 UI 中文文案作为请求枚举 |
| 可空值 | 未完成时间、未结束住宿等使用 `null`；列表使用 `[]` | 不把 null 转成字符串 `"null"`；新契约不以空字符串代替无 ID |
| 长度限制 | 标题、正文、姓名、密码、备注等上限由后端补全 | 冻结后分别测 N−1、N、N+1；不能把未约定的长度当成已确认规则 |

## 4 新契约接口目录与字段

**目录状态**：本章整体为建议契约。标识“沿用”表示路径参考 S2，“补充”表示为满足 S1 新增的建议路径或拆分操作；所有请求字段、返回字段、枚举及错误码仍需随正式 API 设计冻结。每个写接口都必须返回成功后的 ID 和状态，或返回 `data=null` 并允许随后查询核对。

角色缩写：A 为 ADMIN，M 为 MANAGER，S 为 STUDENT。M 始终受楼栋范围限制；S 始终受本人或本人当前房间限制。“分页”使用第 3.2 节。只有明确列出的字段允许客户端修改。

### 4.1 登录与账号管理 FR-01

| 接口标识 | 方法与路径 | 角色 | 请求 | 响应核心字段 | 路径来源 |
|---|---|---|---|---|---|
| AUTH-LOGIN | `POST /api/auth/login` | 公开 | `username`、`password` 必填 | `userId`、`username`、`role`；建立登录态 | 沿用 |
| AUTH-LOGOUT | `POST /api/auth/logout` | 已登录 | 无 | null；当前会话失效 | 沿用 |
| AUTH-ME | `GET /api/auth/me` | A/M/S | 无 | `userId`、`username`、`role`、`studentId`、`managedBuildingIds` | 沿用 |
| AUTH-PASSWORD | `PUT /api/auth/password` | A/M/S | `oldPassword`、`newPassword` 必填 | null；后续会话策略见第 12 章 | 沿用 |
| USER-LIST | `GET /api/users` | A | 分页，可选 username、role、status | 分页账号摘要，不含密码和凭据 | 沿用 |
| USER-CREATE | `POST /api/users` | A | username、password、displayName、role 必填；学生须 studentId | id、username、role、status | 沿用 |
| USER-STATUS | `PUT /api/users/{id}/status` | A | `status`：ENABLED 或 DISABLED | id、status | 补充 |
| USER-RESET | `PUT /api/users/{id}/password/reset` | A | `newPassword` 必填 | null；该账号旧会话全部失效 | 补充 |
| USER-BUILDINGS | `PUT /api/users/{id}/buildings` | A | `buildingIds` 数组，可为空；仅用于宿管 | userId、managedBuildingIds | 沿用 |

账号角色采用 ADMIN、MANAGER、STUDENT；账号一人一角色；学生账号与档案一对一。新建时验证登录名唯一、学生绑定唯一、角色合法。授权数组去重或明确拒绝重复项，不产生重复有效授权。不允许通过普通学生请求创建账号或提升角色。响应中的 `managedBuildingIds` 对非宿管可为空数组，`studentId` 对非学生可为 null。

### 7.1 并发执行方法

### 8.2 数据复核清单

- 在同一数据快照和授权范围内，启用床位总数 = 已占用床位数 + 可分配床位数；不同范围或不同时间点的查询不得直接相减。
- 以有效住宿分别按学生和床位分组，出现大于 1 的分组数都必须为 0；不能只核对 API 返回的汇总。
- 全校床位占用率按合计数量计算；所有百分比只在最终一步按冻结的舍入规则保留一位小数。
- 报修完成量依据 completedAt，晚归依据 businessDate，卫生依据有效初检日期，调宿依据成功办理时点及目标楼栋。
- 业务更正、作废后重新查询；记录数据库复核语句、绑定参数、结果、快照时间及对账差异。只读 SQL 须按实际表结构编写。

## 9 前后端联调操作和断言示例

### 9.1 最短联调顺序

1. 选择同一契约版本、认证模式和测试数据批次，验证登录、AUTH-ME、退出、401 与 403。
2. 管理员创建资源和学生，查询并保存真实 ID；宿管核验完整学号和可分配床位。
3. 入住→查询当前住宿与床位→同栋调宿→查历史→退宿，逐次比较快照。
4. 学生提交报修→宿管受理及完成→学生查看；再跑来访签离、晚归、卫生复查、公告。
5. 执行越权、过期页面、重复操作、并发及事务故障测试，最后独立核算统计。

### 9.3 Postman 断言

下例仅用于第 4 章建议契约的入住成功请求。变量写入当前环境，不把真实会话导出到共享文件。

```javascript
pm.test("HTTP 200", () => pm.response.to.have.status(200));
const body = pm.response.json();
pm.test("入住成功且字段正确", () => {
  pm.expect(body.code).to.eql(0);
  pm.expect(body.data.id).to.be.a("string").and.not.empty;
  pm.expect(body.data.status).to.eql("ACTIVE");
  pm.expect(body.data.studentId).to.eql(pm.environment.get("student1Id"));
  pm.expect(body.data.bedId).to.eql(pm.environment.get("bedA1Id"));
});
if (pm.response.code === 200 && body.code === 0 && body.data?.id) {
  pm.environment.set("stayId", body.data.id);
}
```

越权请求单独断言 403 和无泄漏；无写入须再查询对象核对，不能只靠这一段脚本证明。

```javascript
pm.test("越权拒绝", () => pm.response.to.have.status(403));
const body = pm.response.json();
pm.test("无成功业务结果", () => {
  pm.expect(body.code).not.to.eql(0);
  pm.expect(body.data).to.eql(null);
});
```

### 9.4 前端联调检查

| 场景 | 前端应验证 | 后端应验证 |
|---|---|---|
| 登录或退出 | 登录后读取真实角色；退出清理当前页面缓存；401 不反复重试形成循环 | 登录态真实建立或失效；不信任客户端角色 |
| 403 | 展示无权限反馈，清除不再可见的数据；不能只隐藏按钮 | 每次请求独立鉴权，详情和统计也受限 |
| 写入成功 | 以响应或重新查询的真实状态刷新列表、床位和统计 | 成功意味着事务已提交 |
| 重复点击与冲突 | 提交中禁用按钮；409 后重新查询，不无条件重放调宿等写请求 | 单人单床约束和状态迁移在服务端保证 |
| 时间及空值 | 凌晨业务日期显示正确；null 百分比显示“—”；未结束时间不显示 Invalid Date | 返回约定格式、时区和可空值 |
| 过期页面与缓存 | 授权撤销、公告下架、调宿后刷新可见范围；路由回退不直接复用旧敏感数据 | 最新范围与业务状态重新校验 |
| 内容与头像 | 公告和错误文本安全渲染；受保护图片的加载方式与认证匹配 | 不依赖前端转义代替输入校验，资源访问同样受控 |

## 10 接口字段与数据库的核对

本章对照当前工作区 SQL 的字段和查询说明，供后端实现及测试对账使用。这里只做静态核对，不代表 SQL 或接口已经执行验证。数据库约束不能替代请求鉴权、状态流转和事务校验。

### 10.1 主要映射

| API 字段或语义 | 当前数据库结构 | 联调检查 |
|---|---|---|
| 启用状态 ENABLED/DISABLED | sys_user、student、楼栋、房间、床位用 status=1/0 | 服务端显式映射，不让前端混用布尔值、数字与字符串 |
| managedBuildingIds | manager_building 的有效授权 | 每次请求按最新授权校验；撤销及恢复授权保留审计 |
| 学生 college、className | student.college、class_name 为非空列 | 新增 API 必填；学号、姓名及这些业务必填字段须校验空白 |
| 用户 displayName | sys_user.display_name 为非空列 | USER-CREATE 明确传入，不能遗漏后导致数据库错误 |
| floors、楼栋 genderLimit | dorm_building.floors、gender_limit | 楼层正数；房间楼层不超过总楼层；入住同时满足楼栋与房间限制 |
| 床位占用及容量 | dorm_bed.status 仅启停；stay_record 为生效关系 | availability 和房间容量由查询推导，不接受客户端直接覆盖 |
| endedAt、previousStayId | stay_record.checkout_at、transfer_from_id | 接口字段映射清楚；调宿的旧结束与新入住时间一致 |
| 活跃住宿唯一性 | active_student_id、active_bed_id 生成列及唯一索引 | 并发冲突转换为可处理错误；不能返回原始数据库异常；多条 ENDED 历史允许 |
| 报修退回与类别 | repair_order.status 使用 REJECTED；category 使用 WATER/ELECTRIC/FURNITURE/OTHER | 请求、响应、筛选和页面字典一致；中文仅作为显示标签 |
| 报修完成时间 | repair_order.closed_at，且 status=COMPLETED | completedAt 及完成量只对已完成工单取该值；撤销、退回也有 closed_at，但不计完成量 |
| 报修结果或原因 | repair_order.close_remark、accepted_by、closed_by | 受理、完成、退回、撤销的操作人及终结说明都要写入；撤销无输入说明时由服务端记录默认说明 |
| 晚归 businessDate | late_return_record.business_date 为生成列 | 服务端按业务时间校验；拒绝客户端覆盖生成列或用自然日替代 |
| 卫生 status 与 resultStatus | hygiene_check.status 是 VALID/VOIDED；合格与整改状态根据初检及最近复查计算 | API 分开返回记录有效性与业务结果，不把 PASSED 等写入存储 status |
| 公告状态 | DRAFT/PUBLISHED/WITHDRAWN | 重新发布时清理旧下架状态字段，保留必要审计 |
| 乐观锁与凭据版本 | 主要表 version；sys_user.credential_version | 会话校验读取最新凭据版本；是否向 API 暴露 version 及冲突处理须冻结 |
